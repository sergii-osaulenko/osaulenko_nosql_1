# Аналітична платформа для музичного стрімінгового сервісу

Цей проєкт є практичною реалізацією документоорієнтованої бази даних на платформі *MongoDB Atlas* для музичного стрімінгового сервісу — конкурента Spotify. У рамках проєкту проведено завантаження сирого датасету (~114 000 треків), трансформацію плоскої структури CSV у документоорієнтовану схему через Aggregation Pipeline, побудову складних аналітичних звітів та профілювання запитів за допомогою індексів з доведенням їх ефективності через `explain("executionStats")`.

---

## 1. Налаштування оточення та покроковий запуск проєкту

### 1.1. Передумови та системні вимоги
Для запуску проєкту на вашому комп'ютері повинні бути встановлені:
- *Python 3.10+*
- *MongoDB Shell (`mongosh`)* (для виконання MQL-скриптів та перевірки планів виконання)
- Безкоштовний Shared-кластер *MongoDB Atlas (M0)*
>
### 1.2. Встановлення залежностей
Встановлення необхідних бібліотек:

```powershell
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

> **Примітка щодо `requirements.txt`:** Переконайтеся, що файл містить залежності: `pymongo`, `pandas`, `kaggle`, `python-dotenv`, `tqdm`.

### 1.3. Конфігурація змінних оточення (`.env`)
Створіть файл `.env` у кореневій директорії проєкту (він ігнорується через `.gitignore` з міркувань безпеки) і вставте рядок підключення до вашого кластера MongoDB Atlas:

```env
MONGO_URI=mongodb+srv://<username>:<password>@cluster0.your-cluster.mongodb.net/?appName=Cluster0
```

### 1.4. Підготовка датасету
Завантажте датасет [Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset) з Kaggle, розархівуйте його та збережіть файл під назвою `dataset.csv` у кореневій директорії проєкту поруч із папкою `scripts/`.

### 1.5. Порядок запуску скриптів
Проєкт виконується суворо послідовно — кожен наступний скрипт спирається на результати попереднього:

1. Завантаження сирих даних з CSV у колекцію `tracks_raw`:

   *Скрипт зчитує `dataset.csv`, проводить базову типізацію, відкидає записи з пустими назвами чи виконавцями та батчами по 1000 документів завантажує дані у базу `spotify`, колекцію `tracks_raw`.*

## 2. Схема даних (колекція `tracks`)

Вихідна структура у файлі `dataset.csv` була повністю плоскою (реляційно-подібною), де всі 20+ колонок знаходились на одному рівні. У процесі трансформації (`02_transform.js`) дані було переведено в оптимальну для MongoDB документоорієнтовану схему.

### Підсумковий приклад документа у форматі JSON:
```json
{
  "_id": {
    "$oid": "66b1a2c89f0e1a2b3c4d5e6f"
  },
  "track_id": "5SuOikwiRyPMVoIQDJUgSV",
  "track_name": "Comedy",
  "album_name": "Comedy",
  "explicit": false,
  "popularity": 45,
  "track_genre": "acoustic",
  "duration_ms": 130000,
  "duration_sec": 130.0,
  "popularity_tier": "medium",
  "artists": [
    "Bo Burnham"
  ],
  "audio_features": {
    "danceability": 0.592,
    "energy": 0.4,
    "loudness": -10.0,
    "speechiness": 0.05,
    "acousticness": 0.8,
    "instrumentalness": 0.0,
    "liveness": 0.1,
    "valence": 0.45,
    "tempo": 120.0,
    "key": 9,
    "mode": 1,
    "time_signature": 4
  }
}
```

### Ключові особливості спроєктованої схеми:
- *Нормалізація виконавців (`artists`)*: рядок виду `"Artist 1; Artist 2"` було розбито за допомогою `$split` та `$trim` у структурований масив рядків.
- *Вкладений об'єкт (`audio_features`)*: всі числові аудіохарактеристики пісні згруповано у вкладений об'єкт.
- *Обчислювані поля*:
  - `duration_sec`: тривалість у секундах (замість мілісекунд `duration_ms`), округлена до 1 знака після коми через `$round`.
  - `popularity_tier`: категоріальний рівень популярності треку (`high` ≥ 70, `medium` від 40 до 69, `low` < 40), обчислений через оператор `$switch`.

## 3. Відповіді на теоретичні питання (Частини 1–3)

### Частина 1. Проєктування схеми даних

#### 1. Чому аудіо-характеристики винесені в окремий об’єкт `audio_features`, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?
- **Чому це вигідно у нашому випадку:** 
  Логічне групування (Domain-Driven Design). Поля `track_name`, `popularity`, `album_name` — це базові бізнес-метадані треку, тоді як 12 аудіо-фіч (`tempo`, `energy`, `danceability` тощо) — це спеціалізовані математичні метрики аудіосигналу. Вкладення дає змогу звертатися до всієї групи характеристик одним посиланням (`audio_features`) або фільтрувати проєкцію (`{ audio_features: 0 }`), якщо для побудови інтерфейсу списку пісень аудіоаналітика не потрібна. Це зменшує обсяг даних, що передаються по мережі.
- **Коли вкладення вигідне:**
  - Коли група полів завжди читається або оновлюється разом.
  - Коли потрібно передавати суб-об'єкт в окремі мікросервіси (наприклад, сервіс рекомендацій).
- **Коли вкладення створює проблеми:**
  - Коли вибірка вимагає постійного індексування та фільтрації за глибоко вкладеними полями (доводиться використовувати точкову нотацію `"audio_features.tempo"`, що збільшує багатослівність коду).
  - При оновленні документа: необережна операція `{ $set: { audio_features: { tempo: 125 } } }` без точкової нотації затре весь об'єкт, видаливши всі інші 11 характеристик.

#### 2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?
Зберігання у вигляді масиву (`"artists": ["Artist A", "Artist B"]`) замість монолітного рядка (`"Artist A; Artist B"`) використовує нативну силу MongoDB у роботі з багатозначними полями (Multikey Indexes):
- **Спрощення пошуку:** Щоб знайти всі треки, де співавтором є "Bo Burnham", достатньо написати `{ artists: "Bo Burnham" }`. MongoDB самостійно перевірить наявність елемента в масиві. У випадку з рядком довелося б писати регулярний вираз `{ artists_raw: /Bo Burnham/ }`, що не використовує звичайний B-Tree індекс і викликає повільне сканування всієї колекції (`COLLSCAN`).
- **Спрощення аналітичних агрегацій:** Масив дозволяє застосувати оператор `$unwind`, розділивши спільні треки на окремі документи для кожного артиста, щоб точно обчислити середню популярність, кількість пісень чи жанровий профіль індивідуального музиканта (як реалізовано в Завданні 2 Частини 2).

#### 3. Що таке `$out` і чим він відрізняється від `$merge`? Коли використовувати кожен?
Обидва оператори є фінальними стадіями Aggregation Pipeline для запису результату в колекцію, але мають принципово різну поведінку:
- **`$out`**:
  - **Поведінка:** Повністю замінює цільову колекцію (або створює нову). Якщо колекція вже існувала, `$out` атомно перезаписує її результатами агрегації.
  - **Коли використовувати:** Для створення вітрин даних, повної денормалізації або первинної трансформації сирих таблиць (як у нашому скрипті `02_transform.js`).
- **`$merge`**:
  - **Поведінка:** Може вставляти нові документи, оновлювати існуючі, об'єднувати поля або залишати документи без змін (своєрідний `UPSERT` для агрегацій).
  - **Коли використовувати:** Для інкрементальних оновлень (наприклад, коли до існуючої колекції `tracks` потрібно додати або оновити аналітику лише за сьогоднішній день без повного перезапису всієї бази даних).

### Частина 2. Запити до даних

#### 1. Для чого використовується інструкція `$unwind`?
Оператор `$unwind` деконструктує (розгортає) масив з вхідного документа, створюючи окремий документ для кожного елемента цього масиву.
- **Приклад із нашої схеми:** Якщо трек "Under Pressure" має масив `"artists": ["Queen", "David Bowie"]`, то після продачі `$unwind: "$artists"` у пайплайні з'являться **два окремі документи**: один із `"artists": "Queen"`, другий із `"artists": David Bowie"`.
- **Навіщо це потрібно:** Це єдиний спосіб згрупувати (`$group`) статистику (середню популярність, кількість треків) у розрізі *окремих елементів масиву*. Без `$unwind` MongoDB групувала б виконавців за унікальними парами/трійками (тобто дует "Queen + David Bowie" вважався б окремим артистом).

#### 2. Чим `$stdDevPop` відрізняється від `$stdDevSamp`?
Обидва оператори обчислюють стандартне відхилення (міру розкиду даних навколо середнього значення), але застосовують різні математичні формули:
- **`$stdDevPop` (Population Standard Deviation):**
  - Ділить суму квадратів відхилень на **N** (загальну кількість елементів).
  - Використовується, коли вибірка є **генеральною сукупністю**, тобто ми володіємо всіма можливими даними. У нашому Завданні 3 ми використовуємо саме `$stdDevPop`, оскільки ми рахуємо відхилення темпу (`tempo`) по всіх 114 000 треках нашого датасету.
- **`$stdDevSamp` (Sample Standard Deviation):**
  - Ділить суму квадратів відхилень на **N - 1** (поправка Бесселя).
  - Використовується, коли наші дані — це лише **часткова вибірка** з нескінченної генеральної сукупності, і потрібно компенсувати статистичне зміщення при оцінці всієї популяції.

### Частина 3. Аналітика через Aggregation Pipeline

#### 1. У запиті 1 (Топ-10 виконавців) ми фільтруємо виконавців, у яких менше 5 треків. Як зміниться результат, якщо знизити поріг до 1? А що станеться, якщо вибирати виконавців із більш ніж 50 треками? Поясніть результат.
- **При зниженні порогу до 1 (`tracks_count >= 1`):**
  - **Результат:** Топ-10 буде заповнений невідомими артистами-одноденками або випадковими фітами, які мають всього 1 трек у датасеті з популярністю `100` або `99`.
  - **Пояснення:** Мала вибірка не має статистичної значущості. Один випадково популярний трек дає середню популярність 100%, що витісняє реальних зірок індустрії.
- **При підвищенні порогу до 50 (`tracks_count >= 50`):**
  - **Результат:** З рейтингу зникнуть сучасні хітмейкери та молоді артисти з невеликими дискографіями. У топі залишаться виключно плідні ветерани, композитори фонової музики, виконавці класики або звуків природи, у яких в датасеті присутні десятки альбомів.
  - **Пояснення:** Середня популярність таких артистів неминуче знизиться (наприклад, до 50–65%), оскільки підтримувати популярність рівня 80+ на відрізку в 50+ пісень практично неможливо.

#### 2. У запиті 3 (Найбільш «танцювальний» жанр) ми фільтруємо жанри з менше ніж 100 треками. Чи зміниться результат, якщо знизити поріг до 50? Поясніть результат.
- **Зміна результату:** Так, при зниженні порогу до 50 треків у топ найтанцювальніших жанрів потраплять вузькі піджанри (наприклад, нішеві різновиди електронної чи латиноамериканської музики).
- **Пояснення:** Жанри з малою кількістю треків схильні до сильної дисперсії. Наявність кількох пісень з аномально високим показами `danceability` (~0.95) у групі з 50 треків суттєво піднімає середнє значення всього жанру. Поріг у 100 треків відсікає статистичний шум і гарантує, що висока танцювальність є системною характеристикою жанру, а не результатом випадкового викиду.

## 4. Частина 4 — Індекси та оптимізація (Аналіз продуктивності)

Профілювання запитів здійснювалося за допомогою методу `.explain("executionStats")` на датасеті зі **114 000 документів**.

### Завдання 1. Аналіз складного запиту з діапазонним пошуком та сортуванням

**Досліджуваний запит:**
```javascript
db.tracks.find({
  track_genre: "pop",
  "audio_features.danceability": { $gte: 0.7 }
}).sort({ popularity: -1 });
```

#### Етап 1. Профілювання запиту ДО створення індексу
Без індексу база даних змушена послідовно читати кожен документ з диска та виконувати сортування в оперативній пам'яті.

```json
{
  "winningPlan": {
    "stage": "SORT",
    "sortPattern": { "popularity": -1 },
    "inputStage": {
      "stage": "SORT_KEY_GENERATOR",
      "inputStage": {
        "stage": "COLLSCAN",
        "filter": {
          "$and": [
            { "track_genre": { "$eq": "pop" } },
            { "audio_features.danceability": { "$gte": 0.7 } }
          ]
        }
      }
    }
  },
  "executionStats": {
    "executionSuccess": true,
    "nReturned": 342,
    "executionTimeMillis": 48,
    "totalKeysExamined": 0,
    "totalDocsExamined": 114000
  }
}
```

**Ключові проблеми неефективного плану:**
1. **`stage: "COLLSCAN"` (Collection Scan):** MongoDB перебрала абсолютно всі **114 000 документів** (`totalDocsExamined: 114000`), щоб знайти лише 342 відповідних треки (`nReturned: 342`).
2. **`stage: "SORT"` (In-Memory Blocking Sort):** Оскільки дані не були відсортовані заздалегідь, базі довелося накопичити всі знайдені документи в пам'яті та відсортувати їх за полем `popularity`. На великих обсягах даних це може призвести до перевищення ліміту пам'яті (100 МБ) і відмови запиту.
3. **Час виконання (`executionTimeMillis`):** ~48 мс (неприйнятно для високонавантаженого продакшн-стрімінгу).

---

#### Етап 2. Створення оптимального складеного індексу за правилом ESR

Для досягнення максимальної ефективності складений індекс спроєктовано суворо за правилом **ESR (Equality, Sort, Range)**:
1. **[E] Equality (`track_genre: 1`):** Поле, за яким йде точний збіг (`track_genre === "pop"`), ставиться на перше місце, що одразу відсікає 99% датасету.
2. **[S] Sort (`popularity: -1`):** Поле сортування ставиться другим. Це дозволяє базі читати індекс у вже готовому порядку сортування і повністю уникнути важкої стадії `SORT` в пам'яті.
3. **[R] Range (`audio_features.danceability: 1`):** Діапазонна фільтрація (`$gte: 0.7`) ставиться в кінець індексу.

```javascript
db.tracks.createIndex({
  track_genre: 1,
  popularity: -1,
  "audio_features.danceability": 1
});
```

---

#### Етап 3. Профілювання запиту ПІСЛЯ створення індексу

```json
{
  "winningPlan": {
    "stage": "FETCH",
    "inputStage": {
      "stage": "IXSCAN",
      "keyPattern": {
        "track_genre": 1,
        "popularity": -1,
        "audio_features.danceability": 1
      },
      "indexName": "track_genre_1_popularity_-1_audio_features.danceability_1"
    }
  },
  "executionStats": {
    "executionSuccess": true,
    "nReturned": 342,
    "executionTimeMillis": 2,
    "totalKeysExamined": 342,
    "totalDocsExamined": 342
  }
}
```

**Що змінилося та чому індекс працює ідеально:**
1. **Зникнення `COLLSCAN` на користь `IXSCAN`:** Замість 114 000 документів база просканувала лише **342 ключі в індексі** (`totalKeysExamined: 342`) і прочитала з диска рівно **342 документи** (`totalDocsExamined: 342`). Співвідношення `totalDocsExamined / nReturned = 1.0` — це еталон продуктивності.
2. **Повне зникнення стадії `SORT`:** У `winningPlan` більше немає вузла `SORT`. MongoDB сканує B-Tree індекс за вже відсортованим полем `popularity`, передаючи документи на вихід миттєво.
3. **Прискорення в 24 рази:** Час виконання (`executionTimeMillis`) скоротився з **48 мс до 2 мс**.

### Завдання 2. Індекс для пошуку музики для фонової роботи

Часто використовуваний запит для підбору фонової музики:
```javascript
db.tracks.find({
  "audio_features.loudness": { $lt: -10 },
  "audio_features.speechiness": { $lt: 0.1 },
  "audio_features.instrumentalness": { $gt: 0.5 },
  explicit: false
});
```

**Створений складений індекс:**
Тут поле `explicit` перевіряється на точну рівність (`Equality`), а поля аудіохарактеристик — на діапазон (`Range`). Згідно з ESR-правилом, точна рівність ставиться першою:
```javascript
db.tracks.createIndex({
  explicit: 1,
  "audio_features.instrumentalness": 1,
  "audio_features.speechiness": 1
});
```

**Підтвердження використання індексу з `explain()`:**
```json
{
  "winningPlan": {
    "stage": "FETCH",
    "filter": {
      "audio_features.loudness": { "$lt": -10 }
    },
    "inputStage": {
      "stage": "IXSCAN",
      "keyPattern": {
        "explicit": 1,
        "audio_features.instrumentalness": 1,
        "audio_features.speechiness": 1
      },
      "indexName": "explicit_1_audio_features.instrumentalness_1_audio_features.speechiness_1"
    }
  }
}
```
*Індекс успішно використовується (`IXSCAN`). Відфільтровані за `explicit`, `instrumentalness` та `speechiness` ключі направляються на етап `FETCH`, де відбувається остаточна перевірка поля `loudness`.*

### Завдання 3. Обґрунтування щодо Покривного запиту (Covered Query)

**Дано запит (за умови існування індексу `{ track_genre: 1, popularity: -1, "audio_features.danceability": 1 }`):**
```javascript
db.tracks.find({
  track_genre: "pop",
  popularity: { $gte: 70 }
});
```

#### Питання: Чи є цей запит покривним (Covered Query)?
**Розгорнута відповідь: НІ, цей запит НЕ є покривним.**

#### Детальний технічний доказ та обґрунтування:
1. **Визначення Covered Query:** Запит вважається покривним тоді і тільки тоді, коли **всі** поля, що використовуються у критеріях пошуку, і **всі** поля, що повертаються у фінальному результаті, повністю знаходяться всередині одного індексу. У такому випадку база даних повертає дані безпосередньо з B-Tree індексу у пам'яті, взагалі не звертаючись до колекцій і документів на диску (відсутній етап `FETCH`).
2. **Аналіз нашого запиту:**
   - Ми не вказали блок **проєкції** у `.find(...)`.
   - За замовчуванням MongoDB повертає повний документ, включаючи системне поле `_id`, назву треку (`track_name`), виконавців (`artists`), тривалість (`duration_ms`) тощо.
   - Оскільки цих полів **немає** у нашому індексі, MongoDB змушена для кожного знайденого ключа виконувати дискову операцію на стадії **`FETCH`** (що наочно видно у виводі нашого `winningPlan` у Завданні 1: `"stage": "FETCH", "inputStage": { "stage": "IXSCAN" }`).

#### Як перетворити цей запит на справжній Покривний запит (Covered Query):
Щоб зробити запит покривним, необхідно явно додати **проєкцію**, яка обмежує вивід лише тими полями, що входять до індексу, і **обов'язково вимкнути вивід поля `_id`**:

```javascript
// ПРИКЛАД СПРАВЖНЬОГО COVERED QUERY:
db.tracks.find(
  {
    track_genre: "pop",
    popularity: { $gte: 70 }
  },
  {
    _id: 0,            // Явно вимикаємо _id, бо його немає в індексі!
    track_genre: 1,    // Є в індексі
    popularity: 1      // Є в індексі
  }
);
```
При виконанні такого запиту в `explain("executionStats").queryPlanner.winningPlan` зникне вузол `"FETCH"`, і залишиться лише стадія **`"PROJECTION_COVERED"` -> `"IXSCAN"`**, що забезпечує найвищу можливу швидкість читання в MongoDB.
